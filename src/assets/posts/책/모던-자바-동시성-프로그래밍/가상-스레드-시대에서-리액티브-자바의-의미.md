:::callout 🎯 **챕터 목표**
:::callout 가상 스레드와 리액티브 프로그래밍이 동시성 문제 해결에 접근하는 방식의 차이를 이해하는 것을 목표로 한다.
:::callout **블로킹 I/O와 논블로킹 I/O, 이벤트 기반 아키텍처, 그리고 각 접근 방식의 트레이드오프**를 비교한다.
:::callout 이를 통해 **언제 가상 스레드를 선택하고 언제 리액티브 프레임워크를 선택해야 하는지 합리적으로 판단**할 수 있게 된다.
이번 장에서는 <span class="text-red">**리액티브 자바(Reative Java)**</span>를 살펴보려 한다.
효율적인 동시성과 블로킹 I/O 처리에 있어 가상 스레드가 유일한 해법은 아니다.
가상 스레드가 주목받기 전부터 많은 개발자들은 리액티브 프로그래밍을 활용해 논블로킹 기반의 확장성 있는 애플리케이션을 만들어왔다.
이 방식은 `Project Reactor`, `RxJava`, `Eclipse Vert.x` 등과 함께 사용되며 <u>**이벤트 기반, 함수형, 태생적 비동기성**</u>과 같이 완전히 다른 패러다임을 따른다.

## 리액티브 프로그래밍 이해
:::callout ℹ️ **리액티브 프로그래밍, reactive programming**
:::callout - <span class="text-red">**비동기 데이터 스트림**</span>과 <span class="text-red">**변경의 자동 전파**</span>에 중심을 둔 선언적 프로그래밍 패러다임이다.
:::callout - 명령을 순차적으로 수행하는 데 집중하는 대신 <span class="text-blue">**스트림 간의 관계와 데이터가 어떻게 변환되는지 정의**</span>한다.
사용자 입력, 센서 값, 외부 시스템 데이터 등 **시간에 따라 변하는 것이라면 무엇이든 스트림**으로 표현할 수 있다.
스트림의 값이 바뀌면 리액티브 프레임워크가 그 변화를 자동으로 다운스트림에 전파해 관련된 컴포넌트들을 업데이트 한다.
이렇게 하면 비동기 이벤트를 효율적으로 처리할 수 있고 복잡한 이벤트 기반 애플리케이션을 더 단순하게 구현할 수 있다.

> 자바 생태계에서 리액티브 프로그래밍은 주로 `논블로킹`, `비동기 연산`, `이벤트 기반 아키텍처`와 연관된다.


### 리액티브 시스템 선언문
리액티브 선언문은 리액티브 시스템의 정의를 제시하고 용어의 의미를 표준화하려는 목적을 갖는다.
#### 4가지 핵심 원칙

| **원칙** | **설명** |
| ---- | ---- |
| **응답성(responsive)** | 일관되게 빠른 응답을 제공하여 사용자 신뢰를 높이고 오류 처리를 단순화한다. |
| **회복성(resilient)** | 장애가 발생해도 문제를 격리하고 복구를 위임하며 복제를 통해 고가용성을 확보하여 응답성을 유지한다. |
| **신축성(elastic)** | 부하에 따라 동적으로 적응하며 성능 유지를 위해 자원을 효과적으로 늘리거나 줄인다. |
| **메시지 기반(message-driven)** | 비동기 메시징을 활용해 느슨한 결합, 격리, 효율적인 자원 사용을 실현하며 이를 통해 회복성과 신축성을 확보한다. |

### 블로킹 vs 논블로킹
`블로킹`에서는 I/O가 발생하면 호출한 스레드는 해당 작업이 완료될 때까지 기다린다.
`논블로킹` 모델에서는 I/O 연산을 수행할 때도 스레드가 멈추지 않고 다른 태스크를 계속 수행할 수 있다.

논블로킹 시스템에서는 운영체제가 I/O 처리 책임을 맡고 연산이 완료되면 OS가 콜백 함수를 호출하는 방식으로 애플리케이션에 알린다.

#### 예제: HTTP/1.1의 요청 파이프라이닝을 처리하는 HTTP 서버
이 서버는 다음을 수행해야 한다.
- 여러 클라이언트의 연결을 수락
- 복잡도가 각각 다른 HTTP 요청 처리(빠른 연산, 느린 연산)
- kepp-alive 세션을 위한 연결 상태 유지
- 요청 파이프라이닝을 정확히 처리
- 수백 또는 수천 개의 동시 연결을 처리할 수 있는 확장성 확보

#### 1️⃣ 단일 스레드 블로킹 서버
요청이 오래 걸리는 작업(예: 느린 DB 조회)을 수행하면 서버 전체가 블로킹 된다.
다른 클라이언트는 서버에 연결할 수도 없고 요청 처리 결과를 받을 수도 없다.

서버가 클라이언트 요청을 처리하는 동안 호출한 스레드는 클라이언트가 연결을 끊을 때까지 블로킹된다.
클라이언트가 데이터를 더 이상 보내지 않으면서도 연결을 유지하고 있다면 서버는 입력을 기다리며 계속 멈춰있게 된다.
⚠️ 단일 스레드 서버이므로 현재 세션이 끝나기 전까지는 다른 클라이언트는 연결할 수 없다.
- 기존 클라이언트의 세션이 살아있는 상태에서 다른 클라이언트에서 서버에 연결을 시도하면 연결 시도가 블로킹된다.

#### 2️⃣ 멀티스레드를 지원하는 서버
각 클라이언트 요청마다 새로운 스레드를 만들어 연결에 대응하면 동시에 다수의 클라이언트와 연결할 수 있다.

✅ **멀티스레드 서버의 핵심 개선사항**
- 요청을 처리할 수 있도록 **고정된 수의 스레드 풀** 생성
- 각 연결은 개별 스레드에서 실행되어 동시에 다수의 요청을 처리할 수 있다.
- 개별 연결을 통해 들어오는 요청 한 건의 처리는 여전히 순차적으로 진행되어 적절한 파이프라인 구조를 유지하지만 여러 개의 연결은 동시에 처리된다.

**고정 크기를 가진 스레드 풀을 생성해 동시에 클라이언트가 연결될 수 있도록 했다.**
더 많은 클라이언트를 처리하기 위해 스레드 수를 늘릴 수도 있지만 가상 스레드가 등장하기 전에는 한계가 있다.
- 플랫폼 스레드는 비용이 크다
- 일정 수준을 넘어서면 스레드 수를 늘려도 성능이 더 좋아지지 않는다.
이런 문제는 가상 스레드를 사용하여 확장성을 높일 수 있다.
- 최소한의 오버헤드로 매우 많은 동시 연결을 처리 가능

#### 3️⃣ **NIO (new input / output)**
:::callout ℹ️ 가상 스레드 이전의 대안: **NIO (new input / output)**
:::callout - `JDK 1.4`에서 도입된 `준비 상태(readiness)기반의 논블로킹 API`로 스트림 중심의 java.io를 버퍼 중심의 채널과 Selector 이벤트 루프로 대체한다.

:::callout 💡 **자바 I/O와 NIO 간단 비교**
:::callout 자바는 두 가지 방식으로 I/O를 처리할 수 있다.
:::callout - 전통적인 `java.io` 패키지와 현대적인 `java.nio`
:::callout - 자바 I/O는 스트림 기반이며 일반적으로 블로킹 방식이다.
:::callout - 자바 NIO는 버퍼 기반이며 논블로킹을 지원해 대용량 데이터 전송과 고성능 애플리케이션에서 더 높은 확장성을 제공한다.

✅ **논블로킹 버전의 핵심 개선사항**
- 서버 채널을 논블로킹 모드로 설정
- 단일 스레드가 이벤트 루프를 통해 모든 I/O 이벤트를 처리
- 새로운 연결은 스레드를 블로킹하지 않고 수락된다.
- 데이터 읽기/쓰기는 논블로킹으로 수행된다.
이벤트가 감지되거나 타임 아웃이 만료되면 서버가 이벤트나 대기중인 업데이트를 처리할 수 있게 된다.
단일 스레드로 동작함에도 불구하고 여러 연결을 동시에 처리할 수 있다.
- 각 연결마다 별도의 스레드를 생성하지 않고도 다수의 클라이언트를 효율적으로 관리할 수 있다.

### 이벤트 기반 아키텍처
`이벤트 기반(event-driven)` 패러다임 위에 구축된 많은 프레임워크가 존재하며 이를 통해 동시성과 확장성을 효율적으로 처리하는 일이 쉬워졌다.
- `Netty`, `Vert.x`

#### Vert.x
`Vert.x`의 경우는 본질적으로 <u>**이벤트 루프 기반 동시성 모델을 사용하는 멀티코어 리액터 패턴**</u> 위에 구축된다.
**소수의 가벼운 이벤트 루프 스레드**가 `NIO`와 같은 논블로킹 연산을 통해 지속적으로 I/O 이벤트를 대기하고 처리한다. 요청 인입 같은 이벤트가 발생하면 짧고 논블로킹인 콜백이 이벤트 루프 안에서 실행되어 높은 응답성을 보장한다.

하지만 모든 작업을 이벤트 루프에서 처리할 수 있는 것은 아니다.
현실에는 데이터베이스 쿼리나 파일 시스템 접근처럼 본질적으로 블로킹되거나 오래 걸리는 작업도 존재한다. `Vert.x`는 **이런 작업을 별도의 워커 스레드 풀로 지능적으로 위임하여 이벤트 루프가 느려지는 것을 방지한다. **이런 설계 덕에 이벤트 루프는 불필요한 지연없이 새로운 요청을 계속 처리할 수 있게 된다.

:::callout 💡**이벤트 버스**
:::callout `Vert.x` 의 강점 중 하나는 애플리케이션의 각기 다른 컴포넌트들이 비동기적으로 통신할 수 있도록 해주는 이벤트 버스이다.
:::callout - 시스템을 느슨하게 결합된 상태로 유지하면서도 애플리케이션의 각기 다른 부분을 자연스럽게 조율할 수 있다.
<img src="https://www.notion.so/image/https%3A%2F%2Fprod-files-secure.s3.us-west-2.amazonaws.com%2Fce63075d-cee3-44a7-8d31-efcf5784b0e7%2Fb327958a-d276-4fc6-ba5f-bb397b6781d0%2Fimage.png?table=block&id=392d67b9-9e80-808b-bec2-d0da4e8293a3&cache=v2" alt="image" width="848" height="780" loading="lazy" />

위 그림을 보면 `Vert.x` 같은 프레임워크가 이벤트 루프를 중심으로 어떻게 동작하는지 알 수 있다.
이 프레임워크는 클라이언트 연결을 관리하고 외부 요청을 처리하며 응답을 기록하는 모든 과정을 `논블로킹` 방식으로 수행한다.
일반적으로 이 위에 리액티브 프레임워크가 올라가며 네트워크 연산을 단순화하는 고수준 API를 제공한다.
- 개발자는 저수준의 논블로킹 I/O를 직접 다루는 대신 HTTP 요청과 응답, 카프카 메시지와 같이 추상화된 타입을 사용해 직관적으로 작업을 할 수 있어 개발 과정이 훨씬 단순해진다.

**애플리케이션 코드**는 가장 상위 계층에 위치해 **이벤트 루프와 직접 상호작용하지 않고 ****`이벤트 핸들러`****를 통해 동작한다.**
:::callout ⚠️ **애플리케이션의 이벤트 핸들러는 ****`이벤트 루프 스레드, 즉 I/O 스레드`****에서 실행된다.**
:::callout 만약 이 스레드를 블로킹하는 코드가 있다면 다른 동시 이벤트는 전혀 처리될 수 없다.
:::callout - 반응성과 동시성 처리 능력이 완전히 무너지며 리액티브하게 설계된 시스템에 치명적인 결과를 초래한다.
> 🚀 **해결책: 애플리케이션 코드는 반드시 논블로킹이어야 한다.**
> - **어떤 상황에서도 I/O 스레드를 블로킹해서는 안된다.**


> 🤔 애플리케이션 코드가 논블로킹 상태를 유지하도록 하려면 어떻게 해야 할까?
> → <span class="text-red">**리액티브 프레임워크!! **</span>
> - 블로킹 연산을 피하면서도 복잡한 흐름을 효율적으로 처리할 수 있도록 <span class="text-brown">비동기 API</span>를 제공

### 비동기 API
> <span class="text-red">**비동기 API**</span>는 정확히 무엇이고 어떻게 동작하는 것일까?

대부분의 개발자는 `동기(synchronous) API`에 익숙하다.
```java
public class AiService {
  public String chat(String message) {
     return "Echo: " + message.toUpperCase();
  }
}
```

이 `chat` 메서드를 호출하는 스레드는 응답을 받을 때까지 블로킹된다.
이것이 **동기 API**의 전형적인 특징이다. 호출하는 스레드는 블로킹된 채 기다려야 한다.

#### 🧐 **이 동기 API를 비동기 API로 만드려면 어떻게 해야할까?!?**
→ **결과를 기다리는 대신 메서드가 즉시 반환되도록 하고 결과가 준비되면 콜백 함수가 결과를 처리하게 만들면 된다.**
```java
public void chat(String message, Consumer<String> consumer) {
    Thread.startVirtualThread(() -> {
        try {
            String response = "Echo: " + message.toUpperCase();
            consumer.accept(response);
        } catch (Exception e) {
            consumer.accept("Error during chat: " + e.getMessage());
        }
    });
}
```


#### **비동기 버전 chat 메서드 호출**
```java
aiService.chat("Hello", response -> {
  System.out.println("Response1: " + response);
});

aiService.chat("What is your name", response -> {
  System.out.println("Response2: " + response);
});
```

메인 스레드는 첫 번째 chat 메서드를 호출한 후 결과를 기다리지 않고 두 번째 chat 메서드를 호출한다.
첫 번째 호출에 대한 응답이 준비되면 비동기적으로 처리된다.

:::callout ⚠️ **비동기 실행에서의 콜백 문제: 통합하기 어렵다.**
:::callout - 비동기 실행에서 콜백을 사용하면 코드의 유지 관리성이 급격히 떨어진다.
:::callout - 콜백을 사용하면 할수록 코드를 읽고 관리하기 어려워지는 콜백 지옥에 빠지게 된다.
```java
// 콜백의 응답을 다른 chat 메서드의 인자로 넘기려면..?!
aiService.chat("What is the meaing of life?", response -> {
    aiService.chat(response, response2 -> {
        aiService.chat(response2, response3 -> {
            aiService.chat(response3, response4 -> {
                System.out.println(response4);
            });
        });
    });
});
```


#### 🚀 **자바는 ****`CompletableFuture`**** 라는 대안을 내놓았다.**
- 이를 사용하면 비동기 코드를 구조화되고 조합할 수 있는 방식으로 작성할 수 있어 결과적으로 코드 가독성도 유지할 수 있다.
```java
public CompletableFuture<String> chat(String message) {
    return CompletableFuture.supplyAsync(() -> {
        try {
            return "Echo: " + message.toUpperCase();
        } catch (Exception e) {
            return "Error during chat: " + e.getMessage();
        }
    });
}
```


이 방식을 통해 다수의 비동기 호출을 더 구조화된 방식으로 연쇄적으로 호출할 수 있다.
```java
aiService.chat("What is the meaning of life?")
    .thenCompose(aiService::chat)
    .thenCompose(aiService::chat)
    .thenCompose(aiService::chat)
    .thenAccept(System.out::println);
```

`CompletableFuture`가 비동기 결과를 처리하는데 큰 도움이 되었지만 아직 고려할 사항이 있다.
바로 <span class="text-red">**데이터 스트림**</span>이다.
`CompletableFuture` 가 하나의 결과를 반환하는 메서드에서는 좋지만 한 번의 응답으로 끝나는 것이 아니라 지속적인 데이터의 흐름이라는 연속적인 결과를 처리해야 할 때는 어떨까?
- 데이터 스트림을 비동기적으로 처리하는 분야가 리액티브 프레임워크가 빛을 발하는 분야이다.

## 자바 리액티브 프로그래밍
<span class="text-red">**자바 리액티브 프로그래밍**</span>은 `비동기`, `논블로킹`, `이벤트 기반` 애플리케이션을 중심으로 한 패러다임이다.
이 패러다임의 핵심 개념은 <span class="text-blue">**리액티브 스트림(reactive stream)**</span>이다.
**리액티브 스트림**은 **배압(backpressure)**을 사용해 **비동기 데이터 흐름을 관리하기 위한 표준**이며 리액티브 스트림 명세에 정의되어 있다.
### 리액티브 스트림 이해
리액티브 프로그래밍에서는 <u>**코드를 스트림을 중심으로 구성**</u>하며 변환들의 연결을 `파이프라인`이라고 부른다.
이 패러다임에서 모든 것을 이벤트의 스트림으로 바라볼 수 있으며 이벤트는 생산자에서 소비자로 흘러가면서 여러 변환 단계를 거친다.

무엇이든 이벤트가 될 수 있으며(사용자 클릭, 센서 측정값, 수신된 메시지 등) 이벤트는 `업스트림 소스`에서 `다운스트림 구독자`로 전달되며 그 과정에서 데이터를 변환하거나 필터링하는 `연산자`들을 통과한다.

**연산자는 자신의 업스트림을 관찰하고 새로운 스트림을 생성한다.**
**스트림은 기본적으로 지연 실행된다!!**
- 구독자가 존재하기 전까지는 아무런 처리도 시작되지 않는다.
**비동기**이기 때문에 이벤트가 언제 도착할지 알 수 없으므로 이벤트가 도착했을 때 반응하도록 `관찰자(observer)`를 미리 설정해 둔다.

#### 리액티브 프로그래밍 4가지 기본 구성 요소

| **구성 요소** | **설명** |
| ---- | ---- |
| **발행자(publisher)** | 데이터 항목을 **비동기적으로 발행하는 소스**로 시간의 흐름에 따라 0개 이상의 항목을 발행할 수 있는 데이터 생산자. |
| **구독자(subscriber)** | 발행된 항목을 **수신하고 처리하는 소비자**로 구독자는 데이터를 수신하겠다는 의사를 표현하고 어떻게 처리할 지 정의한다. |
| **구독(subscription)** | 발행자와 구독자를 연결하는 매개체로 데이터 흐름을 관리하고 배압 제어를 가능하게 한다. |
| **프로세서(processor)** | 구독자이면서 동시에 발행자 역할을 하는 구성요소로 스트림에 따라 흐르는 데이터를 변환한다. |

#### 3가지 타입의 시그널
리액티브 스트림은 3가지 타입의 시그널을 발행할 수 있다.

| **시그널** | **설명** |
| ---- | ---- |
| **데이터 항목(data item)** | 스트림을 통해 흐르는 실제값 |
| **에러 신호(error signal)** | 복구할 수 없는 오류가 발생했음을 나타내며 스트림을 종료시킨다. |
| **완료 신호(completion signal)** | 더 이상 발행할 항목이 없으며 스트림이 정상적으로 완료되었음을 나타낸다. |

#### 자바의 여러 리액티브 프로그래밍 라이브러리
1️⃣ **Project Reactor 핵심 타입**
- `Flux<T>`: **0~N** 개의 항목을 발행
- `Mono<T>`: **0**개 또는 **1**개의 항목 발행

2️⃣ **RxJava 핵심 타입**
- `Observable<T>`: **0~N** 개의 항목을 발행
- `Single<T>`: **정확히 1**개의 항목 발행
- `Maybe<T>`: **0**개 또는 **1**개의 항목 발행

#### Project Reactor 예제 (기본적인 리액티브 스트림 파이프라인)
```java
public class ReactiveExample {
    public static void main(String[] args) {
        // 1에서 5까지의 정수를 방출하는 Flux 생성
        Flux<Integer> numbers = Flux.just(1, 2, 3, 4, 5); // ①

        // 스트림처리: 짝수만 필터링하여 선택하고 문자열로 변환
        numbers
                .filter(n -> n % 2 == 0)    // ② 짝수만 선택
                .map(n -> "Value: " + n)      // ③ 문자열로 변환
                .subscribe(
                        System.out::println,      // ④ onNext: 각 값을 출력
                        error -> System.err.println("Error: " + error),  // ⑤ onError
                        () -> System.out.println("Done!")  //⑥ onComplete
                );
    }
}
```

1️⃣ 1~5까지 정수값으로 구성된 **콜드 스트림 생성**
- 이 스트림은 구독자가 구독하기 전까지 아무 값도 출력하지 않는다.
2️⃣ `filter 연산자`는 짝수라는 조건식을 만족시키는 원소만 포함하는 **새로운 스트림을 생성**
3️⃣ `map 연산자`는 각 원소를 정형화된 문자열로 변환한다.
4️⃣ `subscribe 메서드`는 **파이프라인 실행을 유발하고 출력된 값을 어떻게 처리할지 정의**한다.
5️⃣ 파이프라인에 있는 연산 처리 중 예외를 던지면 **에러 처리 콜백을 실행**
6️⃣ 스트림이 모든 원소를 출력하면 완료 콜백을 실행

:::callout 💡 **리액티브 스트림은 자바 스트림과 다르다.**
:::callout - `java.util.stream.Stream`은 컬렉션을 메모리 내에서 동기적으로 처리하는 데 사용하는 **자바 Stream API**
:::callout - 반면 **리액티브 스트림**은 `비동기`, `이벤트 기반`, `논블로킹` 데이터 처리를 다루며 **배압**을 지원한다.
### 배압
리액티브 프로그래밍에서 **배압**은 다운스트림 구독자가 데이터가 더 이상 처리할 수 없을 때 업스트림 발행자에게 <u>**‘너무 빠르다. 천천히!’**</u>라고 신호를 보낼 수 있게 해주는 핵심 메커니즘이다.

#### 높은 빈도로 트레이딩하는 시나리오
```java
public class BackpressureDemo {

    public static void main(String[] args) throws InterruptedException {
        // 초고빈도 가격 피드 시뮬레이션 ①
        Flux<PriceData> extremeFeed = Flux.interval(Duration.ofNanos(100_000))
                .map(i -> new PriceData(
                        "HFT-Exchange",
                        "BTC/USD",
                        50000 + ThreadLocalRandom.current().nextDouble(-100, 100),
                        Instant.now()
                ))
                .share(); // 구독자 사이에 공유되는 핫 스트림

        // 전략 1: 샘플링 - 주기적인 스냅샷 ②
        System.out.println("SAMPLING Strategy:");
        extremeFeed
                .sample(Duration.ofMillis(100))
                .take(10)
                .subscribe(price -> System.out.printf(
                        "[SAMPLED] Price: $%.2f at %s%n",
                        price.price(), price.timestamp()));

        Thread.sleep(1500);

        // 전략 2: 폐기 - 넘치면 폐기 ③
        System.out.println("\nDROP Strategy:");
        AtomicInteger dropped = new AtomicInteger(0);
        extremeFeed
                .onBackpressureDrop(price -> {
                    if (dropped.incrementAndGet() % 1000 == 0) {
                        System.out.printf("[DROPPED] %d updates dropped%n",
                                dropped.get());
                    }
                })
                .publishOn(Schedulers.boundedElastic())  // ④
                .take(Duration.ofSeconds(1))
                .subscribe(price -> {
                    simulateWork(10);  // 느린 처리 시뮬레이션
                    System.out.printf("[PROCESSED] Price: $%.2f%n", price.price());
                });

        Thread.sleep(1500);

        // 전략 3: 최신 값 - 최신 값만 유지 ⑤
        System.out.println("\nLATEST Strategy:");
        extremeFeed
                .onBackpressureLatest()
                .publishOn(Schedulers.boundedElastic())
                .subscribe(price -> {
                    simulateWork(10);  // 아주 느린 처리
                    System.out.printf("[LATEST] Price: $%.2f%n", price.price());
                });

        Thread.sleep(2000);
    }

    private static void simulateWork(int millis) {
        try {
            Thread.sleep(millis);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new RuntimeException(e);
        }
    }

    public record PriceData(String exchange, String symbol, double price, Instant timestamp) {
    }
}
```

1️⃣ 초당 10,000개 항목을 출력하는 스트림 생성 - 초고빈도 거래 데이터 시뮬레이션
2️⃣ **샘플링 전략: 주기적으로 스냅샷을 취하는 방식**
- 모든 항목을 처리할 수 없지만 정기적인 업데이트가 필요할 경우 적합
3️⃣ **폐기 전략: 소비자가 따라가지 못할 경우 폐기**
- 일부 데이터 손실이 허용되는 상황에 적합
4️⃣ `publishOn`은 처리를 다른 스레드 풀로 이동시켜 데이터 생성과 소비를 분리한다.ㅏ
5️⃣ **최신 값 전략: 아직 처리되지 않은 항목 중 가장 최신 값만 유지한다.**
- 현재 상태만이 중요한 경우 이상적

#### 리액터가 제공하는 다양한 배압 처리 전략

| **전략** | **설명** | **사용 / 적합 상황** |
| ---- | ---- | ---- |
| `onBackpressureBuffer()` | 소비자가 따라올 때까지 모든 항목을 버퍼에 저장 | 데이터 손실이 허용되지 않고 메모리가 충분할 경우 사용 |
| `onBackpressureBuffer(maxSize)` | 제한된 크기의 버퍼를 사용하며 한도를 초과시 실패 | 메모리 고갈을 방지하기 위한 안전장치 |
| `onBackpressureDrop()` | 초과된 항목을 조용히 폐기 | 완전성보다 최신성이 중요한 실시간 데이터에 적합 |
| `onBackpressureLatest()` | 가장 최신 항목 하나만 유지 | 중간 값에 의미를 둘 필요 없는 상태 업데이트 시나리오에 적합 |
| `onBackpressureError()` | 배압이 발생하면 즉시 실패 | 배압 자체가 시스템 설계상의 문제를 의미하는 경우 사용 |

### 리액티브 프로그래밍의 장점과 단점
#### 👏 장점
1️⃣ **리액티브 프로그래밍**은 `논블로킹` 연산과 `비동기` 실행에 기반한다.
이를 통해 애플리케이션은 시스템 자원을 최소한으로 소비하면서도 매우 많은 동시 요청을 처리할 수 있다.
- I/O 집중적인 작업의 경우 리액티브 프로그래밍을 활용하면 확장성과 성능을 현저히 높일 수 있다.

2️⃣ **리액티브 프로그래밍**은 **논블로킹, 비동기 코드 작성을 도와주는 강력한 도구 모음**을 제공한다.
그리고 함수형 및 선언적 코딩 스타일을 장려하는데 이는 전통적인 명령형 프로그래밍보다 더 직관적이고 표현력이 좋다.
- 리액티브 코드는 데이터 스트림을 조합하고 이벤트를 구조적으로 처리하므로 효과적으로 사용한다면 가독성과 유지보수성이 더 좋아질 수 있다.

3️⃣ **리액티브 프로그래밍**은 현대적인** 클라우드 네이티브 애플리케이션**과 자연스럽게 통합되며 마**이크로서비스 아키텍처에 특히 적합하다**
- 분산된 컴포넌트 간의 데이터 흐름과 통신을 효율적으로 처리하여 병목을 줄이고 응답성을 향상한다.

#### 👎 단점
1️⃣ **익숙해지기 어렵다.**
전통적으로 기존 프로그래밍과 다른 프로그래밍 패러다임을 사용하기 때문에 익숙해지기 어렵다.
- 명령형 프로그래밍에 익숙한 개발자에게는 학습 곡선이 가파르게 느껴질 수 있다.
- 스트림 조합이나 배압 관리 같은 리액티브 패턴에 적응하려면 사고방식의 전환과 새로운 개념 및 기법에 대한 이해가 필요하다.

2️⃣ **디버깅이 어렵다.**
비동기 실행과 이벤트 기반 데이터 흐름 때문에 오류를 추적하고 실행경로를 이해하기가 쉽지 않다.
- 코드에서 보이는 논리적 흐름과 실제 실행 흐름이 완전히 달라 머릿속으로 추적하는 디버깅이나 IDE 디버깅 모두 난이도가 높아진다.
- 리액티브 코드의 알아보기 힘든 스택 트레이스 내용은 디버깅을 훨씬 더 복잡하게 만든다.

3️⃣ **CPU 집중적인 작업**
리액티브 프로그래밍은 I/O 집중적인 작업을 처리하는 데 매우 뛰어나지만 가상 스레드와 마찬가지로 CPU 집중적인 작업에는 이상적인 선택이 아니다.
